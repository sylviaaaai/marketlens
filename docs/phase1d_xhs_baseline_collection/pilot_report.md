## 3. 接口与20+10可行性

真实两次健康检查均自报v2.5.5，两次登录检查均已登录。核对当前暴露的MCP工具定义、本地接口数据字典和固定v2.5.5源码；源码链接及参数映射见[能力说明](README.md#评论能力结论)。本地未发现Go源码checkout，未修改第三方程序、Docker配置或Cookie。

`load_all_comments=false` 不主动滚动或展开，只读取已经加载的评论。源码存在以一级DOM评论数量为目标的有限滚动：HTTP使用嵌套`comment_config.max_comment_items`，MCP工具对应`limit`，均需`load_all_comments=true`才生效。**不能把名字中的all解释成必须无限加载，也不能把参数limit误当作数据库裁切要求。** 此能力只做源码核对，本轮未启用，未宣称真实追加验证成功。

二级`reply_limit`/`max_replies_threshold`仅跳过单个回复过多的展开按钮，不能控制每篇合计追加10条。没有独立cursor评论分页工具。因此完整“20+10有限追加策略”尚不能由现有接口直接落实。本轮按授权回退：默认返回、额外评论请求0、已经取得的有效评论全部存储。软目标记录在Plan/Task中，不充当存储上限。

前两篇作为默认返回能力观察样本（包含在5篇Pilot中，无额外请求）：分别耗时8.391秒、5.890秒，均为10条一级+5条二级，hasMore=true。没有为了达到20+10重新访问。其余3篇是正常Pilot详情采集，不是新增的评论扩展实验。
